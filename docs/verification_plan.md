# 持ち込みライブラリの全件検証計画

## 目的と範囲

`experiments/library/` と `experiments/library3/` の持ち込み C++ を全件調査し、各関数・型について、正本 C++ と対応する Lean 証明、C++ テスト、テンプレートと依存部品を順に include した確認を揃える。公開条件は `AGENTS.md` と `docs/architecture.md` に従う。

初期調査では、前者にヘッダ48件・テストドライバ46件・テンプレート C++ 2件、後者にヘッダ20件・テストドライバ19件・テンプレート C++ 2件がある。合計68ヘッダには重複実装があるため、最終的な部品数とは異なる。テンプレート内の補助関数、内部の計算に必要な関数、既存の手動テスト・無視指定テストも調査対象とする。

現在の AST bridge は `merge_sort` と `associative_array` に特化している。これは既存基盤の不足であり、今後も部品ごとの専用変換を増やす方針ではない。対応する C++ の部分言語について、共通の AST → 中間表現 → Lean 生成器を整備する。部品固有なのは仕様・不変条件・証明とし、変換規則は構文・型・操作に対して定義する。ソースと Lean モデルの意味対応、および利用する STL 操作の契約は明示した信頼境界として扱う。

## 作業順序

1. **全件台帳と現状確認**
   - 元パス、宣言、依存先、用途、既存テスト、重複候補を列挙し、全元ファイルから検証先への対応を残す。
   - 元の2系列は個別にコンパイル確認する。関数テンプレートは使用例を具体化し、未使用の宣言もテストの不足として記録する。
   - `python3 tools/check_public.py` で既存2部品の基準状態を確認する。
   - 台帳には「未調査」「不具合あり」「C++ テスト済み」「共通変換器対応済み」「Lean 証明済み」「include 確認済み」「公開済み」を別項目として記録する。

2. **仕様・重複・命名の整理**
   - 同名でも意味や API が異なる実装は区別する。重複する各実装を調査・テストした上で、同じ仕様は共通の公開部品に統合し、元実装との対応と変更点を記録する。
   - 持ち込みライブラリの用途と命名を優先する。公開ファイル・部品 ID は既存の snake_case、公開宣言は専用名前空間を基本とし、型名・関数名の変更は対応表に記す。
   - 既存 `merge_sort` と `associative_array` は当面、検証基盤の回帰確認として保持する。衝突が判明した場合に改名・移動等を行い、登録、証明、テスト、文書を一緒に更新する。
   - 入力範囲、空入力、添字、算術の範囲、型の代数的条件、所有権、グラフの条件等を定める。不具合は小さい再現ケースを作って修正する。

3. **検証経路を段階的に拡張**
   - 最初の小さな部品で、C++ 整備から共通変換器、Lean、テスト、公開登録までを一巡させる。
   - 中間表現には C++ の整数幅・符号、評価順序、状態とメモリ、停止条件、基本演算と領域の費用を表現する。対応範囲を限定し、その外の構文を拒否する。
   - ソース全体のハッシュや部品名を変換規則の選択に使わない。同じ対応構文を使う別関数、ローカル変数の改名、定数・演算の変更が、対応する Lean 検証対象の変更として自動生成されることを確認する。
   - 未対応ノード・演算の拒否と、故意の境界条件・演算変更による検証失敗も確認する。汎用とは対応部分言語に対する汎用性を意味し、任意の C++ 全体への対応を前提にしない。
   - 登録基盤の「bridge は部品ごとに別ファイル」という制約を撤廃し、既存2部品も共通生成器へ移行する。専用 bridge は移行中の回帰確認に限って保持する。
   - 必要な構文と STL 操作ごとに、意味・前提・時間・追加領域の契約と対応範囲を文書化する。テンプレート、可変状態、再帰、ラムダ、ポインタ、128 bit 整数などは使う部品に合わせて対応する。
   - 未対応構文・宣言やソース変更を検出して検証を止める。ハッシュ更新だけで意味対応をレビュー済みと扱わない。
   - 独立に書いた同じアルゴリズムの Lean 証明だけでは完了としない。公開 C++ の実装と対応づける。

4. **依存順に全分野を検証**

   | 段階 | 対象 | 主な検証事項 |
   | --- | --- | --- |
   | A | テンプレート補助、代数構造、配列、区間、文字数、Union-Find | 型の条件、境界、更新の不変条件、償却計算量 |
   | B | 比・行列、ModInt・DynamicModInt、整数商列挙・floor_sum、乱数生成 | 除算条件、オーバーフロー、法変更、状態遷移 |
   | C | BIT、Segment Tree、Lazy Segment Tree、doubling | 半開区間、単位元、合成順、更新・探索、費用・領域 |
   | D | 辺・グラフ表現、最短路、MST、トポロジカル順序、閉路、Lowlink、木 | 非連結、多重辺・自己辺、負辺・負閉路、再帰の深さ |
   | E | フロー、順序集合・多重集合、Segment Tree Beats | 残余グラフ、メモリ所有権、乱択の仮定、償却解析 |
   | F | 幾何、素数判定・因数分解、Rolling Hash、畳み込み | 数値誤差、退化入力、整数範囲、停止、衝突確率、NTT/CRT の条件 |

   実際の順序は台帳の依存グラフに従って調整する。後半の難しい部品も全件の対象に含め、前半のみの完了を全件完了と報告しない。

5. **部品ごとの完了条件**
   - C++ からの検証対象生成と公開宣言・ソース照合。
   - Lean による結果、停止、未定義動作の不在、時間・追加領域の上界の証明。乱択は、必要な仮定の下で各入力を固定した期待時間と誤答確率も扱う。
   - 独立した参照実装との比較、小規模網羅、境界・不具合再現ケース、固定シードの差分テスト。所有権や整数演算に関係する部品は sanitizer でも確認する。
   - `a.cpp` は撤廃する。ライブラリ内のテンプレート、依存部品、対象部品の順に include したテストコードをコンパイルし、機能を実行する。複数部品を同時に include して名前衝突も確認する。現在は持ち込みの `small_template.hpp` を使い、他のテンプレートも台帳で追跡・検証して必要なら統合する。
   - メタデータ、仕様文書、Lean import、テスト、bridge を登録し、`python3 tools/check_public.py` を通す。証明に `sorry` や未説明の公理がないことを監査する。
   - 全条件を満たしたものから `library/` へ移す。未完了のものは理由と残作業を明記して `experiments/` に保持する。

6. **全件の完了確認**
   - 元ファイル・宣言の台帳と公開登録を突き合わせ、取りこぼしを検査する。統合した実装も対応先を確認する。
   - GCC 13.3.0、C++17、固定 Lean/Clang の環境で全件検証と公理監査を実行する。
   - 利用問題・ケース・制限が確定した部品は管理環境で性能測定し、実測値と環境情報を `benchmarks/local/` に保存する。
   - 最終報告に、検証範囲、統合・改名、不具合修正、信頼前提、実行結果、未完了項目があればその内容を示す。

7. **ヘッダだけの配布と自動更新**
   - `library/` 以下の `.hpp` だけを、相対パスを保持した `library-hpp.zip` にする。TOML、証明、テスト、実験コード、Git 履歴は含めない。利用者は clone せずに Release asset を取得できる。
   - テンプレートも検証完了後に `library/` 内の `.hpp` として配置し、公開ヘッダから配布物外への依存をなくす。
   - `main` への push ごとに検証を実行し、全検証成功後に固定タグ `headers` の Release asset を更新する。PR と手動実行は配布物の検査まで行う。失敗時は直前の成功版を保持する。
   - 更新ジョブを直列化し、既に新しい main のコミットがある場合は旧コミットによる更新をスキップする。Release 本文に配布元コミットを記載する。
   - ZIP の内容が公開ヘッダと完全に一致すること、および ZIP の展開先だけを include パスに指定したコンパイルを確認する。

## 実行上の条件

- ケース内容は生成スクリプトまたは専用ファイルに置き、TOML/YAML は参照だけを持つ。 入力は `in/*.txt`、期待出力は `out/*.txt` に統一する。
- テストと CI はコンテストサイトと通信しない。検証コマンドは Linux の seccomp でソケット通信を禁止し、設定できなければ実行を止める。ツール準備と Release 更新に必要な GitHub 等への通信は検証処理から分離する。
- スタイルは旧 `a.cpp` 相当のマクロと `using namespace std` を使用してよい。`a.cpp` 自体は復活させず、必要な定義はライブラリ内のテンプレートに持たせる。
- ローカルで生成したケースを先に使う。公式問題データの取得が必要な場合は適用ルールを先に確認し、テスト・CI から取得処理を分離する。この環境から提出しない。
- 元コードとユーザーの変更を保持し、無関係な編集は避ける。
- コミット・push を行う場合は `docs/agent/git_workflow.md` に従い、push したコミットの Actions が完了するまで結果を確認する。

## 現時点の進捗

全体構成、ファイル件数、ローカル include の参照先、既存検証基盤を調査した。`a.cpp` を削除し、検査と文書をテンプレートを先に include する方式へ変更した。変更後も `python3 tools/check_public.py` が全検証を通過した（既存2部品の機能・入出力テスト、テンプレート単体・依存順・全部品同時の include、既存 AST bridge、Lean ビルド、`leanchecker`）。共通変換器と持ち込みコードの全件コンパイル・テスト・Lean 証明は未完了。

ヘッダのみの ZIP 生成・検査、検証時の通信禁止、main push 後の Release 自動更新を実装した。GitHub 上の自動更新はこの変更が push された後に確認する。

ローカルで、通信禁止下の公開2部品の全検証、ZIP の収録内容と展開先だけでのコンパイル、余計なファイルを含む ZIP の拒否、IPv4/IPv6・TCP/UDP ソケットの禁止と子プロセスへの継承を確認した。Release スクリプトは模擬 GitHub CLI で新規作成・既存更新・旧コミットのスキップを確認し、YAML 構造とシェル構文も確認した。GitHub 上の実行結果は未確認。
