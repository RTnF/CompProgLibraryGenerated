# 構造とワークフロー

## 現在の段階

公開部品は `library/merge_sort.hpp` と `library/associative_array.hpp`。それぞれにソース固有の Clang 構文木チェックと信頼済み Lean モデル、Lean 証明、C++ テスト、依存結合器、実測記録がある。汎用の C++ 検証器はまだない。新しい部品は専用の検証経路が揃うまで `experiments/` に置く。

## 領域

| パス | 用途 |
| --- | --- |
| `a.cpp` | `solve()` より前に部品を貼る作業用テンプレート |
| `library/` | 証明とテストを終えた公開 C++ 部品とメタデータ |
| `experiments/` | 未証明の試作。公開対象外 |
| `Proofs/`, `Proofs.lean` | Lean の仕様、生成された検証対象、証明 |
| `verifier/` | Clang 構文木から Lean の検証対象を作る基盤 |
| `tests/` | C++ の仕様テストと結合後の貼り付けテスト |
| `benchmarks/` | 問題・ケース・制限に結び付く測定手順と結果 |
| `tools/` | 公開判定、依存解決、コード結合などの補助ツール |
| `.github/workflows/` | 単一 C++ 環境と Lean の CI |

将来の公開部品は一つの C++ ファイルと隣接する機械可読のメタデータを持つ。メタデータには依存先、仕様と証明の参照先、ソース識別情報を記録する。部品間の依存は非循環とし、結合器は必要な依存先を先に、一度ずつ出力する。公開 C++ は必要な標準ヘッダを明示し、専用の名前空間に本体を置く。検証用の注釈や専用構文は入れない。標準ライブラリ以外の外部ライブラリへの依存は認めない。

## 公開まで

1. 実装と仕様を `experiments/` で検討し、前提条件、境界条件、入力サイズ、依存先を定める。
2. C++ ソースを正本として、固定バージョンの Clang 構文木から検証対象を生成する。対応可能な C++ 構文だけを公開対象にする。
3. すべての公開関数・型について、前提条件下の結果、停止、未定義動作の不在、時間と追加領域の計算量を Lean で証明する。時間は基本演算と採用した STL 操作契約から数える。乱択では各入力を固定した期待時間、最悪時の追加領域、必要なら誤答確率の上界を証明する。
4. 単体の C++ テストと、依存を結合して `a.cpp` の `solve()` より前に貼った結果のコンパイル・テストを行う。
5. 対応先とソース変更の検出、証明、テスト、依存グラフ、結合結果のすべてが CI を通ってから `library/` へ移す。`sorry`、未説明の公理、手書きの同等アルゴリズムの証明だけでは公開条件を満たさない。

`tools/public.py` は公開部品とメタデータ、依存グラフ、参照ファイルを検査し、貼り付け先の C++ を生成する。CI は C++ テストと生成結果のコンパイル、Lean ビルド、各部品のソース対応チェックを直列に行う。マージソートの対応チェックは `verifier/merge_sort_bridge.py` が担う。

## 信頼境界

証明は、固定した C++ フロントエンドとソースから検証対象への変換、コンパイラ、使用する C++ 標準ライブラリ操作の契約が正しいことを前提にする。STL の契約は使用する操作ごとに結果、前提条件、時間・領域の費用を記録し、呼び出し側で前提条件を証明する。STL の「平均計算量」を使う場合は、その平均の仮定を個別に記す。仮定を示せない場合は最悪計算量を使う。

現在のマージソート変換器は、レビューした一つの Clang 構文木を Lean のリスト演算に対応付ける。構文木の一致を機械的に確認するが、**構文木から Lean モデルへの意味対応そのものは証明されていない**。対応の正しさを信頼前提として明示する。利用する `std::vector<int>` 操作とその契約、割り当て成功の前提は [マージソートの記録](merge_sort.md) に記す。

乱択アルゴリズムの証明で独立一様な抽選を用いる場合、それは明示的な信頼前提であり、C++ の乱数エンジンから無条件に導かれる保証ではない。各証明が利用する前提と、検証器・ツールチェーンの版を追跡する。

## コンパイルと実測

標準の C++ コンパイル確認環境は GCC 13.3.0、`-std=c++17 -O2 -Wall -Wextra -pedantic` の一つとする。CI は GCC 13.3.0 コンテナを使い、Lean は別ジョブで `lean-toolchain` の版を使う。4サイトのコンパイラ設定は同一ではないため、この確認は各サイトでの動作保証を意味しない。サイト固有の確認をした場合は環境と結果を個別に記録する。

実測は問題、入力ケース、制限時間・メモリ制限が定義された場合に行う。小さな固定ケースは保存し、大きなケースは出典・生成方法・検証用の値を残す。実行環境、コンパイラ、オプション、実装、入力規模、測定方法、時間・メモリを記録し、候補の優劣が規模によって変わる場合は規模別に示す。測定環境情報と実測値は Git の追跡対象外である `benchmarks/local/` に保存し、リポジトリには測定手順と入力の確認値を残す。性能比較には管理した測定環境を使い、通常の GitHub Actions ランナーの数値を採用しない。対応する問題がなく未測定でも、証明とテストを満たせば公開できる。

この環境はコンテスト参加用 VM と隔離されている。この環境からコンテストへ提出しない。問題やテストケースの取得・利用では各サイトのルールを守る。
