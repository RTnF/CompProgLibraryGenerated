## 許可公理の管理

`verification/allowed_axioms.json` を唯一の許可リストとする。初期値は `propext`、`Classical.choice`、`Quot.sound`。各項目に名前、定義の構造指紋、理由を記録する。構造指紋は宣言の種類、所属モジュール、型、宇宙パラメータ、安全性から計算し、固定 Lean の標準環境から採取したものに一致させる。名前が同じでも型を書き換えた公理は許可しない。

公理の定義検査と、証明の公理依存検査を区別する。定義または許可項目が変わった公理だけを定義検査する。初回とキャッシュがない場合も検査する。成功した結果を `.cache/axiom-definitions.json` に保存する。CI はこのファイルを保存・復元し、実行時に実際の定義指紋と項目を再比較する。未変更の項目は定義検査を省略する。削除した項目に依存する証明は、依存検査で拒否する。

証明の依存検査は毎回行う。`verification/InspectEnvironment.lean` が実際の宣言の型と値をたどるため、`#print axioms` の表示やエクスポート済み公理キャッシュの自己申告だけに依存しない。間接依存、private 宣言、opaque 宣言も扱う。不許可の公理、欠けた宣言、unsafe な依存を拒否する。`sorryAx` と `Lean.trustCompiler` は許可リストに含めない。許可リストを変更するだけでは、Proofs 内の独自 `axiom` 宣言や native_decide を許可しない。

## 公理以外の検査

1. **危険なソース構文**: コメントと文字列を除去したうえで、`sorry`、`native_decide`、`unsafe`、`extern`、`implemented_by`、`partial`、初期化処理、独自 elaborator/macro、実行コマンド、カーネル検査の省略を拒否する。Proofs の import は登録した Proofs と固定ツールチェーンの Init/Std に限る。登録外のサブディレクトリに置いた Lean ファイルも登録ゲートで拒否する。
2. **新規ビルド**: Proofs のソースを一時ディレクトリへコピーし、固定の最小 Lake 設定で最初からビルドする。プロジェクトの既存 olean、Lake キャッシュ、任意のビルド設定は持ち込まない。ソースのスクリーニングをビルド前に行い、`LEAN_ABORT_ON_PANIC=1` を設定する。
3. **仕様の保持**: `verification/statements.json` は公開証明モジュールの定理文と、そこから型・計算定義・帰納型・構成子を通じて到達する定義の構造指紋を固定する。現在は生成された等式定理を含む275定理と1,605宣言（公開部品 `bit_width_u64` と `doubling` の登録で追加）。定理の証明項を変更することは許すが、命題を True に弱める、前提を強める、参照先の定義を書き換える、定理を削除する変更は拒否する。型・宇宙・安全性も比較する。第二カーネルに渡す公開名は現在 ASCII の識別子に限定し、未対応の公開名は検査を省略せず拒否する。新しい公開部品の証明を追加した場合も登録した全定理とマニフェストの集合を照合する。
4. **Lean カーネルの再検査**: 新規ビルドの `Proofs` に対し `leanchecker --fresh Proofs` を実行する。空の環境から import を含む全宣言を再生する。通常のモジュール単位の leanchecker とは検査範囲が異なる。
5. **独立カーネル**: 同じ成果物から lean4export で公開宣言と依存を出力し、Rust 実装の nanoda に渡す。同じ許可リストを読み、不許可公理は使用の有無にかかわらず拒否する。nanoda の型規則へのパッチは行わない。型検査成功だけでなく、エラーのない成功メッセージも確認する。未参照の内部補助宣言は Lean の再検査で扱い、第二カーネルの範囲は出力した公開宣言と依存である。
6. **C++ との対応**: 既存の公開宣言登録、共通生成モデルの全文照合、部品固有 bridge、C++ テスト、include 検証を維持する。定理の証明が正しくても別の C++ を証明していては公開条件を満たさない。

定義指紋を更新する時は、元の定理の型と変更された定義を確認する。検査失敗を解消する目的でマニフェストを自動更新する処理は用意しない。許可リストと検査器・仕様マニフェストはレビューする側の信頼境界であり、それらを同時に改変する攻撃を自身の設定で防ぐとはしない。定理や中間結果が人間の意図する意味を持つか、C++ とモデルの対応、STL 契約の妥当性は内容のレビューも必要である。既存2部品の専用 bridge が共通変換器へ移行済みとは扱わない。

Lean 4.34.1、Lean カーネル、nanoda、exporter、検査ツール、固定標準ライブラリ、OS/ハードウェアを信頼前提として明記する。二つのカーネルの結果が一致しても、検査ツールや仕様の誤りがなくなったと断定しない。
