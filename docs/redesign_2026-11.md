# 検証方式の見直し（2026-11-11 決定）

## 背景

- 全件 CI を 30 分以内に終える必要がある（4 コアの GitHub ランナー）。
- 2026-11-11 時点の `Proofs/` は 1036 モジュール・23 MB。公開部品は約 60。
- 最大の原因は `segment_tree_beats` である。749 行のヘッダに対し、`BeatsExec*` が 89 モジュール・9.9 MB（全体の 42%）、Beats 系全体では 225 モジュールある。中身はアルゴリズムの推論ではなく、C++ を文ごとに記号実行した経過である。15 本の vector を持つ状態を実行し、`s64.valid`/`i32.valid` の仮定を文ごとに運んでいる。
- この方式では、証明量が「コード行数 × 状態の大きさ」に比例して増える。
- CI run 42994061436 の計測:
  - Lake をコア数で並列化した後も、全ビルドは約 22 分（1310〜1387 秒）かかった。並列化前の冷えたビルドは 44〜80 分だった。
  - 最終監査（kernel 再生・独立 kernel）は約 10 分かかった。
  - 各ジョブの所要時間は約 36 分だった。
- 部品が増えるほど悪化するので、方式を変える。

## 決定事項

1. **正しさの意味**: 2 層に分ける。
   - **モデル層**: アルゴリズムを Lean の純粋関数（モデル）で書き、仕様に対する正しさと計算量を証明する。
   - **対応層**: C++ は制限した構文で書く。その構文の意味論を一度だけ定義し、C++ から Lean の関数へ機械的に翻訳する。翻訳結果がモデルと一致すること（または翻訳結果が直接仕様を満たすこと）を証明する。
   - C++ を文ごとに記号実行する証明は作らない。
2. **整数の範囲**: 値は数学的な整数（`Int`/`Nat`）として扱う。「入力と途中の値が型の範囲に収まる」という前提を部品ごとに一度だけ述べ、各演算の範囲は証明しない。折り返しを使う部品（xorshift、rolling hash、mod61 など）だけを `UInt64` などの意味論で証明する。
3. **オブジェクト寿命と領域**: C++ のコピー・ムーブ・破棄の監査や、C++ ヒープ上の領域上界の証明はやめる。未定義動作は ASan/UBSan 付きのテストで確かめる。
4. **計算量**: モデル上の操作回数とデータ量について、オーダー（`O(f(n))`。ある定数 `c`, `n₀` で抑えられること）を証明できればよい。厳密な定数は求めない。乱択は期待値のオーダーでよい。

## 翻訳の対象

- **関数**: 自由関数と、メンバー関数を持つクラスを扱う。クラスは「フィールドの組を状態とする Lean の構造体」と「メンバー関数ごとの状態変換」に翻訳する。
- **制御**: `for`/`while`（範囲 for を含む）、`if`、`return`、`break`/`continue` を扱う。ループは Lean の `for ... in` か、停止性の示せる再帰に翻訳する。
- **データ**: スカラーは `Int`/`Nat`/`Bool`。`std::vector` は `Array`、`std::pair` は `Prod` に翻訳する。STL の使える操作は文書で列挙し、それ以外は翻訳器が拒否する。
- **型テンプレート**: `T` は Lean の型変数と型クラス（演算の性質を仮定として持つ）に翻訳し、元の汎用性を保つ。
- **計算量の計測**: 翻訳器が操作回数を数える版（tick を加える版）も生成する。

翻訳器そのものの正しさは証明しない。代わりに、翻訳規則を文書化し、翻訳結果を Lean で実行した結果と C++ の実行結果を突き合わせる差分テストで確かめる（信頼境界として `docs/trust_policy.md` に記載する）。

## 予算

| 項目 | 目標 |
| --- | --- |
| `Proofs/` の総量 | 3 MB 以下（目安） |
| 全ビルド（4 コア、冷えた状態） | 10 分以下 |
| 最終監査 | 8 分以下 |
| CI 全体（push から完了まで） | 30 分以下（全ビルドを含む） |

部品を登録するときに、ビルド時間の増分を測って記録する。予算を超える部品は、証明を見直すまで公開しない。

## 移行

1. 新しい翻訳器と意味論を小さい部品（`fenwick_tree`、`union_find`、`cumulative_sum`）で作り、旧方式と並べて検証する。
2. 部品ごとに新方式へ移し、旧方式の証明（`Proofs/` の該当モジュール、`verifier/` の該当変換、テスト）を削除する。
3. 重い部品（`segment_tree_beats`、`lazy_segment_tree`、`monoid_lazy` など）は最後に移す。
4. 全部品の移行後、旧方式の共通基盤（`CppMove*`、寿命監査、`s64.valid` を運ぶ実行モデル、`statements.json` の旧定理）を削除する。

移行中も CI を 30 分以内に保つため、旧方式の `segment_tree_beats` の証明（全体の 42%）を最初に外し、新方式で再検証するまで同部品を `experiments/` に戻して「検証待ち」とする（2026-11-11 決定）。
