# 信頼境界の方針（2026-10-08 決定）

利用者の決定に基づく。実装は未着手の項目を含む。

## 1. 標準ライブラリの契約

- 標準ライブラリ（`std::vector` の操作、`std::sort`、`std::lower_bound`、`std::priority_queue`、`std::map` など）の動作は、**明示した契約**として信頼してよい。libstdc++ の内部実装は検証しない。
- 契約は結果と計算量を述べる仕様として一覧にし、レビュー済みのものだけを Lean の公理として置く。例: `std::sort` は並べ替えで、昇順になり、比較は O(n log n) 回。
- 契約公理は `verification/allowed_axioms.json` の通常の公理とは別の区分（`stl_contract`）で登録し、証明検査（`tools/check_proof_security.py`）が名前・文言・理由を照合する。契約公理に依存する定理は「証明済み」ではなく「STL 契約の下で証明済み」と台帳に記録する。
- 実装（2026-10-11）: 契約公理は `verification/stl_contracts.json`（名前・定義のハッシュ・規格の条項・理由）に登録し、定義は `Proofs/StlContracts.lean` に置く。`tools/check_proof_security.py` は通常の公理（`allowed_axioms.json`）と別に読み込み、定義のハッシュを照合し、契約に依存する定理の件数と例を出力する。結果の値（並べ替え後の列など）は公理にせず、モデルの定義とする方針で、公理にするのは標準が漸近的にしか述べない計算量の上界だけ（`docs/stl_contracts_plan.md`）。
- 契約の追加は、仕様の根拠（規格の条項）と、必要な前提（比較関数が狭義弱順序であることなど）をレビューしてからにする。
- 変換器は、契約が登録された操作だけを受け入れる。未登録の操作は従来どおり拒否する。
- 割り当て成功、GCC 13.3 / x86_64 Linux / C++17 / LP64 の整数変換、C++ から Lean への変換の意味対応は、これまでどおり信頼前提として明記する。

- `assert` はモデル上で失敗する検査（`NStmt.check`）として扱い、有効（`NDEBUG` なし）であることを前提にする。定理は「前提を満たす入力では全部の `assert` が通り、結果が正しい」ことを述べる。前提違反で必ず停止することは、必要な部品だけ個別に証明する。`NDEBUG` で `assert` を消すと、前提違反は未定義動作になる。

## 2. 浮動小数

- 検証の対象外にはしない。競技プログラミングで許される誤差（絶対誤差または相対誤差が 1e-7 以下など）を単位に、結果の仕様を記述する。
- Lean の基準モデルは有理数 `Rat` か、誤差の予算を持つ区間で表す。IEEE 754 のビット単位の完全な再現は目標にしない。
- 誤差が蓄積する計算（FFT、逐次の累積、条件数の大きい計算）は、丸め誤差の見積もりを定理に含める。見積もりができないものは「誤差未証明」として台帳に明記し、証明済みと扱わない。
- `sqrt`、`log`、`cos` などの数学関数は、誤差の上界つきの契約（1. と同じ区分）として扱う。

## 3. 範囲

- 台帳の全宣言を目標にする。期限（2026-11-08 ごろ）までに終わらない部分は、未対応の理由と順序を台帳に残す。
- 標準出力（`print`、`operator<<`）は副作用なので、まず入出力の契約（書き出す文字列を仕様に持つ）として扱う方式を検討する。

## 4. Mathlib（2026-10-08 決定）

利用者の決定に基づき、Lean の証明で Mathlib を使ってよい。Mathlib は、Mathlib の版を更新するごとに、このプロジェクトの基準で 1 回だけ検査し、結果をログに残す。その後は信頼する。

- 依存は `lakefile.toml` の `require` で、Lean のツールチェーンと同じ版の `v4.34.1` に固定し、実際のリビジョンは `lake-manifest.json` に記録する。版を上げるときは、ツールチェーンと同時に上げる。
- 1 回の検査は `python3 tools/audit_mathlib.py` で行う。対象は `verification/mathlib_audit_modules.txt` のモジュールの import 閉包（Mathlib 全体は輸出ツールのメモリに収まらないため、証明が使う分野に絞った一覧）。基準は、自前の証明と同じ「許可した公理だけを使うこと」「Lean のカーネル（`leanchecker`）と独立カーネル（`nanoda`）の両方で通ること」である。Mathlib と依存パッケージの安全な宣言は、許可していない公理（`sorryAx`、`Lean.ofReduceBool` など）を参照してはならない。Lean 本体の内部だけが参照する `Lean.trustCompiler` と `lcProof` は環境の公理として許可し、`unsafe` 宣言が参照する分は、安全な宣言から到達できないので除外する。
- 結果は `verification/mathlib_audit_log.json` に、Mathlib のリビジョン、ツールチェーン、対象モジュールと閉包に含まれるモジュールの一覧、検査した宣言数、書き出しのハッシュ、検査器のコミット、日付つきで追記する。版を上げたとき、またはモジュール一覧を広げたときは、検査をやり直してログをコミットする。
- 日常の `tools/check_proof_security.py` は、現在のリビジョンとツールチェーンに合う記録があり、`Proofs` が import する Mathlib 側のモジュールがすべてその記録の対象に入っていることを確かめる。入っていなければ、検査のやり直しを促して失敗する。記録がそろっている間は Mathlib の中身を信頼する。ただし今のところ、日常の検査も Mathlib の宣言を含む閉包を独立カーネルで通している（約 7 分）。時間が問題になったら、監査済みの Mathlib の定理を公理に置き換えて省く。
- 証明の取り込みは `import Mathlib.…` に限る（`tools/proof_security.py` の `audit_source`）。`Proofs/` の自前のソースには、従来どおり `sorry`、`axiom`、`native_decide`、`macro` などを置かない。公理の許可リスト（`verification/allowed_axioms.json`）は変えない。
- `tools/check_proof_security.py` の一時プロジェクトは、同じ `lake-manifest.json` と、リポジトリの `.lake/packages`（ビルド済み）を使う。取得（`lake update`、`lake exe cache get`）はテスト・CI の実行経路の外で行い、`check_public.py` は通信しない。

- CIは独立scratchの`.lake/build`と、成功したC++/bridge/共有検査の依存fingerprintを再利用できる。scratchのソース監査・同期・Lakeによる入力照合と、各検査の現在の入力・ツールによるfingerprint照合は毎回行う。リポジトリ側のproject oleanをscratchへ持ち込まない。キャッシュの保存元はmainへのpush実行に限り、後続検査が失敗しても成功済み部分を保存する。試行ごとのkeyで途中経過を更新し、変更入力と未成功の検査は再実行する。最終proof-securityの成功結果とkernel replayのmodule cacheはCIへ復元せず、固定仕様・公理依存と両kernelを毎回確認する。保存・復元は検証の通信禁止経路の外で行う。キャッシュがない場合に全工程が7200秒へ収まる保証ではなく、時間切れ後も検証済み部分を失わないための仕組みである。
- 新しい補題は、まず Mathlib にあるものを探し、なければ書く。既存の証明は書き換えない。
